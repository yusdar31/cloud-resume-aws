Kubernetes Pod Scheduling Strategies dan Node Affinity: Panduan Praktis untuk Production

Belum lama ini, tim kami menghadapi masalah klasik di Kubernetes cluster: pod database production keburu ditaruh di node yang sama dengan workload batch processing yang sangat resource-intensive. Hasilnya? Latency naik drastis dan alert pun berbunyi. Dari situ saya sadar betapa pentingnya memahami pod scheduling strategies dan node affinity untuk menghindari insiden serupa.

Di artikel ini, saya akan share pengalaman dan praktik terbaik dalam mengontrol bagaimana pod di-schedule ke node tertentu di Kubernetes. Kita akan bahas dari konsep dasar sampai implementasi di production.

Mengapa Pod Scheduling Itu Penting?

Secara default, Kubernetes scheduler akan menempatkan pod ke node yang tersedia berdasarkan resource request, constraint, dan beberapa faktor lain. Tapi dalam skenario nyata, kita sering butuh kontrol lebih spesifik. Misalnya:

  • Workload latency-sensitive harus di node dengan SSD
  • Database butuh node dengan memory besar
  • GPU workload hanya bisa jalan di node tertentu
  • Compliance requirement mengharuskan data tertentu di region spesifik

Tanpa strategi scheduling yang tepat, bisa jadi workload critical kita "berkumpul" di satu node dan menyebabkan resource contention. Atau lebih parah, pod jalan di node yang tidak memenuhi requirement hardware-nya.

Teknik Scheduling di Kubernetes

Kubernetes menyediakan beberapa mekanisme untuk mengontrol scheduling, mulai dari yang paling sederhana sampai yang paling fleksibel. Mari kita bahas satu per satu.

1. NodeSelector: Cara Paling Sederhana

nodeSelector adalah mekanisme scheduling paling basic. Kita cukup menentukan label yang harus dimiliki node untuk menampung pod tersebut.

apiVersion: v1
kind: Pod
metadata:
  name: api-server
spec:
  nodeSelector:
    disktype: ssd
    zone: production
  containers:
  - name: api
    image: myapp:latest

Pod di atas hanya akan di-schedule ke node yang memiliki label disktype=ssd DAN zone=production. Sederhana, tapi terbatas hanya untuk kondisi AND logic.

2. Node Affinity: Lebih Fleksibel dan Expressive

Node Affinity hadir dengan kemampuan yang lebih powerful. Ada dua jenis node affinity:

  • requiredDuringSchedulingIgnoredDuringExecution — Hard requirement. Pod TIDAK AKAN di-schedule jika tidak ada node yang memenuhi kriteria.
  • preferredDuringSchedulingIgnoredDuringExecution — Soft requirement. Scheduler akan berusaha mencari node yang sesuai, tapi jika tidak ada, pod tetap akan di-schedule ke node lain.

Mari lihat contoh implementasi yang saya gunakan di cluster production:

apiVersion: v1
kind: Pod
metadata:
  name: database-primary
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: node-role.kubernetes.io/database
            operator: Exists
          - key: memory-size
            operator: Gt
            values:
            - "64"
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - key: disk-type
            operator: In
            values:
            - nvme
      - weight: 20
        preference:
          matchExpressions:
          - key: zone
            operator: In
            values:
            - us-west-2a
  containers:
  - name: postgres
    image: postgres:15

Contoh di atas menunjukkan konfigurasi untuk database primary. Pod harus berada di node dengan label node-role.kubernetes.io/database dan memory lebih dari 64GB. Selain itu, scheduler akan mengutamakan node dengan NVMe storage (weight 80) dan zone us-west-2a (weight 20).

Operator yang Tersedia di Node Affinity

Kubernetes menyediakan beberapa operator untuk matchExpressions:

  • In — Nilai label harus ada dalam list values
  • NotIn — Nilai label TIDAK boleh ada dalam list values
  • Exists — Label harus ada (nilai tidak diperhatikan)
  • DoesNotExist — Label tidak boleh ada
  • Gt — Nilai label lebih besar dari value (untuk angka)
  • Lt — Nilai label lebih kecil dari value (untuk angka)

Pod Affinity dan Anti-Affinity

Selain memilih node berdasarkan karakteristik node, kita juga bisa menentukan scheduling berdasarkan pod lain yang sudah berjalan. Ini sangat berguna untuk:

  • Co-locate pod yang sering berkomunikasi untuk mengurangi network latency
  • Spread pod ke node berbeda untuk high availability

Contoh: Pod Anti-Affinity untuk High Availability

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-frontend
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-frontend
  template:
    metadata:
      labels:
        app: api-frontend
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - api-frontend
            topologyKey: kubernetes.io/hostname
      containers:
      - name: api
        image: myapp:latest

Konfigurasi di atas memastikan setiap replica deployment api-frontend berada di node yang berbeda. Jika ada 3 replica, mereka akan tersebar di minimal 3 node. Ini penting untuk menghindari single point of failure.

Pod Affinity untuk Co-location

Untuk skenario di mana kita ingin pod berada di node yang sama dengan pod lain (misalnya application pod dan cache pod):

apiVersion: v1
kind: Pod
metadata:
  name: cache-client
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
          - key: app
            operator: In
            values:
            - redis-cache
        topologyKey: kubernetes.io/hostname
  containers:
  - name: app
    image: myapp:latest

Topology Key: Mengontrol Spread

Topology key menentukan "domain" di mana affinity rule diterapkan. Nilai yang umum digunakan:

  • kubernetes.io/hostname — Level individual node
  • topology.kubernetes.io/zone — Level availability zone
  • topology.kubernetes.io/region — Level region

Untuk cluster multi-zone, kita bisa mengkombinasikan topology key berbeda untuk mencapai spread yang optimal:

spec:
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchExpressions:
            - key: app
              operator: In
              values:
              - web-server
          topologyKey: kubernetes.io/hostname
      - weight: 50
        podAffinityTerm:
          labelSelector:
            matchExpressions:
            - key: app
              operator: In
              values:
              - web-server
          topologyKey: topology.kubernetes.io/zone

Contoh di atas akan memprioritaskan spread di level hostname (weight 100), dan juga mempertimbangkan spread di level zone (weight 50).

Taints dan Tolerations: Mengontrol Akses Node

Seringkali kita ingin node tertentu hanya bisa menampung workload spesifik. Di sinilah taints dan tolerations berperan.

Untuk menandai node bahwa hanya pod tertentu yang boleh masuk:

kubectl taint nodes node-dedicated-gpu dedicated=gpu:NoSchedule

Lalu di pod spec, kita tambahkan toleration:

spec:
  tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"
  containers:
  - name: gpu-workload
    image: ml-training:latest

Effect yang tersedia:

  • NoSchedule — Pod tanpa toleration tidak akan di-schedule ke node tersebut
  • PreferNoSchedule — Scheduler akan menghindari node, tapi tetap bisa menempatkan pod jika tidak ada pilihan
  • NoExecute — Pod yang sudah berjalan akan di-evict jika tidak memiliki toleration

Best Practices dari Pengalaman Production

Setelah mengelola cluster production selama beberapa tahun, ini yang saya pelajari:

  1. Gunakan nodeSelector untuk kasus sederhana. Tidak perlu over-engineering dengan node affinity jika kebutuhan hanya label matching dasar.
  2. Kombinasi required dan preferred affinity. Gunakan required untuk requirement yang tidak bisa ditawar, dan preferred untuk preferensi yang bisa diabaikan jika tidak memungkinkan.
  3. Label node dengan konsisten. Buat standardisasi label di seluruh cluster. Saya biasa menggunakan label seperti node-pool, workload-type, dan hardware-type.
  4. Monitor scheduling failures. Event di Kubernetes bisa memberikan insight mengapa pod gagal di-schedule: kubectl get events --field-selector reason=FailedScheduling
  5. Test dengan dry-run. Sebelum apply ke production, gunakan kubectl apply --dry-run=server untuk memvalidasi konfigurasi.
  6. Jangan lupa resource request. Affinity rules tidak akan bekerja optimal tanpa resource request yang proper. Scheduler butuh informasi ini untuk keputusan placement.

Kesimpulan

Pod scheduling strategies di Kubernetes memberikan kontrol granular atas bagaimana workload kita tersebar di cluster. Node affinity dan pod affinity/anti-affinity adalah tools yang powerful untuk mengoptimalkan performa, reliability, dan resource utilization.

Dari pengalaman saya, kombinasi yang efektif biasanya adalah: gunakan nodeSelector untuk constraint sederhana, node affinity untuk requirement hardware atau zone yang kompleks, pod anti-affinity untuk high availability, dan taints/tolerations untuk dedicated node pools.

Yang terpenting, selalu dokumentasikan keputusan scheduling yang diambil. Trust me, enam bulan dari sekarang kamu akan lupa kenapa pod itu harus di node dengan label tertentu. Sampai jumpa di artikel selanjutnya!
